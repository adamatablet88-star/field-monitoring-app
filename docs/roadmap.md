# מפת דרכים

## מה כבר קיים (פרוטוטייפים, לפי מסמך הצוות)

הפרוטוטייפים הבאים הוצגו/נבנו להדגמה מחוץ למאגר הקוד הזה, ומשמשים בסיס
עיצובי/פונקציונלי לשלב המימוש:

- **דשבורד מגמות** — צפייה בגרפים השוואתיים.
- **קובץ ייצוא לדוח רגולטורי** — Excel לדוגמה תואם דוח אמיתי.
- **מסך הקמת אתר (Admin)** — פרוטוטייפ צפייה בלבד.

כל הפרוטוטייפים הקיימים עבדו על נתוני דמו בזיכרון הדפדפן — ללא שרת,
ללא מסד נתונים אמיתי, ללא שמירה לצמיתות.

## מה עדיין לא נבנה

- טפסי הזנת נתונים בפועל ל-SVE, Bio-venting ודיגום מי תהום (טופס עדשת
  דלק כבר קיים — ראו למטה).
- עריכת ישויות קיימות במסך הקמת האתר (יש create + delete; אין עדיין
  עריכה — למשל תיקון קואורדינטות של קידוח קיים).
- מסך התחברות (Login) אמיתי מול שרת + אכיפת RBAC בצד שרת (מסך הקמת
  האתר פתוח כרגע לכל אחד, ללא הבחנת admin/technician).
- מנגנון פתרון קונפליקטים מלא (יש כבר **זיהוי** קונפליקט — ראו למטה —
  אך אין עדיין ממשק להשוואה/מיזוג/הכרעה, רק סימון "יש קונפליקט").

## מה נבנה

**שלד הפרויקט (שלב 1):**
- **Monorepo** מבוסס npm workspaces: `packages/shared`, `apps/server`,
  `apps/client`.
- **`packages/shared`** — כל הטיפוסים מ-`docs/data-model.md` כקוד
  TypeScript אמיתי (מקור אמת יחיד, מיובא גם ב-client וגם ב-server).
- **`apps/server`** — Express + TypeScript, סכמת Prisma/PostgreSQL
  (הישויות המבניות מלאות; רשומות ביקור כרגע כעמודת JSON לפי הטיפוס
  המשותף, עד שהטופס הרלוונטי ייבנה).
- **`apps/client`** — React + TypeScript + Vite, מסד מקומי (IndexedDB)
  דרך Dexie.js.

**מסד מקומי + סנכרון בסיסי (שלב 2):**
- **`packages/shared/src/sync.ts`** — חוזה הסנכרון (`SyncPushEntry`,
  `SyncPushResult`, `SyncPullEntity`/`SyncPullResponse`), מבוסס
  optimistic concurrency (`version` פר-ישות).
- **`apps/server/src/sync/router.ts`** — `POST /sync/push` (create/
  update/delete עם בדיקת `version` מול השרת; חוסר התאמה ⇒ `conflict`
  עם מצב השרת הנוכחי, לא דריסה שקטה) ו-`GET /sync/pull?since=...`
  (משיכה אינקרמנטלית, כולל "מצבות" למחיקות). מכסה כרגע את חמש הישויות
  המבניות: אתר, קידוח, מיכל, מערכת טיפול, קידוח-תחת-מערכת.
- **`apps/client/src/db.ts`** — טבלת `outbox` (תור פעולות ממתינות)
  וטבלת `syncMeta` (גרסה/עדכון אחרון פר-ישות מקומית, בנפרד ממודל
  התחום עצמו).
- **`apps/client/src/sync.ts`** — `enqueueChange` (כתיבה אופטימית +
  תור), `pushPending`/`pullUpdates`/`runSync`.
- מסך שלד עם אינדיקציית סנכרון חיה (שינויים ממתינים / קונפליקטים) וכפתור
  "סנכרן עכשיו".
- **נבדק מקצה-לקצה מול Postgres אמיתי ובדפדפן אמיתי**: create → applied,
  update עם גרסה נכונה → applied, update עם גרסה ישנה (סימולציה של טכנאי
  שני) → מזוהה כ-conflict ומוצג ב-UI, delete (מצבה) → applied, pull
  אינקרמנטלי לפי `since` מחזיר רק שינויים חדשים.

**Admin: הקמת אתר/קידוחים/מערכות (שלב 3):**
- מסך `apps/client/src/admin/AdminApp.tsx` — ניווט לקוח → אתר → טאבים
  (קידוחי עדשת דלק / מיכלים / מערכות טיפול), עם קידוחי הטיפול/פרמטרים
  תחת כל מערכת נבחרת.
- כל הישויות (`Client` ועד `ParameterConfig`, 7 סה"כ) נערכות דרך אותו
  מנגנון `enqueueChange`/`useLocalCollection` — כלומר גם הקמת האתר
  היא Offline-first, לא רק טפסי השטח.
- **`ParameterConfig` הורחב להיות ישות מסונכרנת עצמאית** (עם `systemId`
  משלה, `version`/`updatedAt`/`deletedAt` בשרת) כדי שאפשר יהיה לערוך
  פרמטר בודד בלי לגעת בכל המערכת — נדרש גם עדכון ל-`packages/shared`,
  ל-schema.prisma (migration) ולסנכרון בשרת ובלקוח. `Client` הורחב
  לאותו סטטוס (ישות מסונכרנת מלאה) כדי שגם יצירת לקוח חדש תהיה
  Offline-first.
- ולידציית `systemLabel` שונה לפי `systemType` ב-UI בפועל: SVE דורש
  פורמט "<מספר> CFM", Bio-venting מקבל טקסט חופשי.
- קלט תעודת הזהות המלאה לקידוח (X/Y/Z, שוחה, עומק/קוטר, מקטע מחורץ)
  משותף (`IdentityFields`) בין קידוחי עדשת דלק לקידוחים תחת מערכת
  טיפול, כנדרש בסבב ההבהרות.
- **נבדק מקצה-לקצה בדפדפן אמיתי**: תרחיש מלא של לקוח → אתר משולב
  (עדשת דלק + SVE) → מיכל → קידוח עדשת דלק עם סקימר אקטיבי ושיוך למיכל
  → מערכת SVE (כולל בדיקה שתווית לא תקינה [ללא "CFM"] חוסמת שמירה) →
  פרמטר עם סף קריטי → קידוח טיפול — סונכרן, ואומת שדה-שדה מול הנתונים
  שנשמרו בפועל ב-Postgres.

**טפסי שטח — עדשת דלק (שלב 4):**
- `apps/client/src/field/` — טאב "טפסי שטח" חדש ב-App הראשי (לצד "הקמת
  אתר"): בחירת אתר → רשימת קידוחי עדשת דלק עם תג סטטוס (בוצע/טרם בוצע
  להיום) → כפתור "הבא" שקופץ לקידוח הבא שטרם בוצע.
- `FuelLensVisitForm.tsx` — עומק מים/מוצר עם חישוב חי של עובי העדשה,
  טוגל "לא נמדד" + סיבה מרשימה סגורה, ותת-טופס שמשתנה לפי אמצעי הפינוי
  של הקידוח (סקימר פאסיבי / סופח / סקימר אקטיבי), כולל **הזיהוי
  האוטומטי**: עדשה קיימת + סקימר ריק ← שני צ'יפים לבחירה מהירה ("לא
  מכוון" / "מפלס ירד מתחת לסקימר"). רשימת פינוי דינמית (אפס/אחת/יותר).
  תמונות לא מומשו (אין עדיין שכבת אחסון קבצים בפרויקט).
- **`FuelLensVisit` הורחב להיות ישות מסונכרנת** (`version`/`updatedAt`/
  `deletedAt` בטבלת `FuelLensVisit` בשרת) — כמו שאר הישויות, כתיבת ביקור
  היא Offline-first. גוף הביקור המלא נשמר כעמודת JSON (כפי שתוכנן
  מראש), לא כטבלה יחסית מפורקת.
- **תוקן באג אמיתי בתשתית הסנכרון תוך כדי הבדיקה**: עריכת אותה ישות
  פעמיים לפני סנכרון ראשון (למשל תיקון "לא נמדד" על ביקור שזה עתה נוצר)
  יצרה שתי רשומות בתור (`outbox`) לאותה ישות — "יצירה" ו"עדכון" עם
  `baseVersion: null` — וכשהשתיים נשלחו יחד, ה"עדכון" חזר כ-conflict
  שקרי מול הגרסה שהוקצתה ל"יצירה" **באותו batch**, וגרוע מזה: מנגנון
  ההתאמה בין תוצאות השרת לרשומות המקומיות (`.find()` לפי entityId) קישר
  את שתי התוצאות לאותה רשומה ראשונה, כך שהעדכון האמיתי נשאר תקוע "pending"
  לנצח בלי שום סימן קונפליקט ב-UI. התיקון: `enqueueChange` ממזג (coalesce)
  עכשיו עם רשומת תור ממתינה קיימת לאותה ישות במקום להוסיף שנייה, ו-
  `pushPending` מתאים תוצאות לפי מיקום ברשימה ולא לפי חיפוש. נתפס ותוקן
  רק כי הבדיקה כללה עריכת ביקור קיים, לא רק יצירה חד-פעמית — תזכורת
  לכסות גם את מסלול ה"עריכה" בבדיקות הבאות, לא רק "יצירה".
- **נבדק מקצה-לקצה בדפדפן אמיתי**: 3 קידוחים בשלושה אמצעי פינוי שונים,
  כולל חישוב עדשה חי, ההצעה האוטומטית, פינוי, ניווט "הבא", ועריכת ביקור
  קיים (לפני סנכרון) — סונכרן ואומת מול הנתונים שנשמרו בפועל ב-Postgres.

היומיומית של הטכנאים).
