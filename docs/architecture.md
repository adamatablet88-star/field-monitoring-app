# ארכיטקטורה

## 1. עקרונות מרכזיים

### Offline-First
הטכנאי בשטח לרוב ללא חיבור רשת יציב. האפליקציה חייבת לתפקד באופן מלא
ללא רשת:

- כל קריאה/כתיבה עובדת מול **מסד נתונים מקומי במכשיר** (client-side DB).
- סנכרון מול השרת מתבצע ברקע, אוטומטית, כאשר הקישוריות חוזרת.
- אין מסך "אין רשת" חוסם — הטכנאי ממשיך לעבוד כרגיל.

### נעילה ופתרון קונפליקטים
שני טכנאים יכולים לבקר באותו אתר/קידוח לפני שהאחד סינכרן. בזמן סנכרון:

- המערכת מזהה קונפליקט (בדיקת `version` בפוש — `apps/server/src/sync/
  router.ts`) ומחזירה את מצב השרת הנוכחי (`serverPayload`) יחד עם
  הקונפליקט, לא רק סימון.
- **ממומש ואכוף בפועל בצד הלקוח** (roadmap שלב 8,
  `apps/client/src/sync/ConflictsPanel.tsx`): מוצג למשתמש שמסנכרן שני
  פאנל עם טבלת שדה-מול-שדה (הגרסה שלי / הגרסה בשרת, שדות שהשתנו
  מודגשים) ושלוש פעולות הכרעה — "השתמש בגרסה שלי" (שולח מחדש, דורס את
  השרת), "השתמש בגרסת השרת" (מבטל את השינוי המקומי, לא שולח כלום),
  "מחק מהתור בלי לשמור" (לקונפליקט-יצירה נדיר בלי `serverPayload`
  להשוואה).
- אין דריסה שקטה של נתונים — כל קונפליקט מחייב הכרעה מודעת של המשתמש;
  שום צד לא מוחל אוטומטית.

### RBAC בסיסי
שני תפקידים בלבד בשלב זה (ראו `docs/data-model.md` להגדרת `Role`),
**ממומש ואכוף בפועל בצד השרת** (`apps/server/src/sync/permissions.ts`,
roadmap שלב 7) — לא רק תיאור כוונה:

| תפקיד | הרשאות |
|---|---|
| `admin` | בונה/עורך מבנה אתרים, קידוחים ומערכות; מוסיף משתמשים; עורך כל נתון היסטורי; עורך קונפיגורציית פרמטרים; מנהל תדירויות ודוחות רגולטוריים |
| `technician` | ממלא ביקורים; מעדכן מצב אמצעי בקידוח קיים; מדווח סטטוס פעיל/לא-פעיל לאתר/מערכת מתוך ביקור בפועל (המקור נחתם בשרת לפי התפקיד, לא נסמך על הלקוח); מתקן רק את הביקורים שהוא עצמו יצר, עד לסוף אותו יום |

התחברות: שם משתמש + סיסמה מול `POST /auth/login`, מחזיר JWT (תוקף 30
יום — טכנאי מתחבר פעם אחת ומשתמש בטוקן המטמון לכל סבב סנכרון, גם בלי
רשת). אין (עדיין) הבחנת הרשאות עדינה יותר משתי הרמות הנ"ל.

## 2. מחסנית טכנולוגית מוצעת

| שכבה | טכנולוגיה | הערה |
|---|---|---|
| Client | React + TypeScript | PWA, מותקן כאפליקציה במכשיר הטכנאי |
| מסד מקומי | IndexedDB (דרך Dexie.js) | תומך שאילתות, אינדקסים, ומודל טרנזקציוני נוח ל-sync queue |
| Sync | תור פעולות מקומי (outbox pattern) + endpoint סנכרון ב-API | כל פעולת כתיבה נרשמת בתור מקומי, נשלחת בסבב סנכרון, מסומנת synced/conflict |
| Server / API | Node.js + TypeScript (REST או tRPC) | |
| מסד שרת | PostgreSQL | טבלאות יחסיות תואמות למודל הישויות; JSONB לקונפיגורציית פרמטרים גמישה |
| אימות | JWT (`jsonwebtoken`) + `bcryptjs` לגיבוב סיסמאות, RBAC ברמת ה-API | ממומש — ראו `apps/server/src/auth/` |
| ייצוא | `exceljs` בצד לקוח (נטען lazy, רק בלחיצה על הכפתור) | ממומש — ראו `apps/client/src/export/`, roadmap שלב 10 |

בחירה זו אינה סופית — היא נקודת מוצא סבירה ל-Offline-first + RBAC + דוחות
Excel, וניתנת לשינוי בתחילת שלב המימוש אם יש העדפה אחרת.

### פריסה

לסביבת בדיקות/הרצה ראשונית (roadmap אחרי שלב 10) הוכנו **שני** יעדי
פריסה חינמיים, שניהם בונים על אותו `createApp()` (`apps/server/src/
app.ts` — ה-API כפונקציה טהורה, בלי `.listen()`, בלי seeding):

- **Render** — שרת אחד מגיש גם את ה-API וגם את קובץ הלקוח הבנוי
  (`apps/server/src/index.ts` מוסיף serving סטטי ל-`apps/client/dist`
  כשהוא קיים, עם fallback ל-SPA, מעל `createApp()`), כדי שלא יהיה
  צורך בשני שירותים נפרדים או בכתובת API שצריך לנחש מראש; הלקוח פונה
  ל-origin של עצמו (`apps/client/src/apiBase.ts`). ראו `render.yaml`.
  **נבדק כאן באופן מלא** — הרצה מקומית אמיתית שמדמה בדיוק את מה
  ש-Render יעשה, כולל דפדפן אמיתי מקצה-לקצה.
- **Netlify** — הלקוח כאתר סטטי (המנגנון הטבעי של Netlify); ה-API
  עטוף כפונקציית serverless יחידה (`netlify/functions/api.cjs`, עם
  `serverless-http` מעל אותו `createApp()`) שאליה מפנים redirects
  ב-`netlify.toml` (`/health`, `/auth/*`, `/sync/*`) — Netlify משמר את
  הנתיב המקורי של הבקשה דרך header פנימי (`x-netlify-original-pathname`)
  כך שה-Express router רואה בדיוק את אותם נתיבים כמו תמיד, בלי
  צורך בקוד שממפה/קוצץ נתיבים. מסד הנתונים חיצוני (למשל Neon), כי
  Netlify לא מארח Postgres בעצמו. קובץ ה-function הוא `.cjs` במפורש
  (לא `.mjs`, לא עוקב אחרי שאר הקוד ב-ESM) — כי הבנדלר של Netlify
  לפונקציות קלאסיות מפיק פלט בפורמט CJS קבוע בשם `.js`, וסיומת `.cjs`
  היא הדרך היחידה להבטיח שNode יפרש את זה נכון בלי תלות באיזה
  `package.json` הכי קרוב יתברר שהוא ה"שכן" של קובץ הפלט בפועל
  (התגלה כבאג אמיתי תוך כדי בדיקה מקומית עם `netlify functions:serve`).
  **הועלה בזהירות רבה יותר**: לא ניתן היה להריץ כאן סימולציה מלאה של
  תהליך הבנייה/פריסה האמיתי של Netlify (`netlify build`/`deploy`
  דורשים חשבון מקושר בפועל) — ראו README.md's "סביבת בדיקות בענן"
  להסבר המלא ולהמלצה להשתמש ב-Render כחלופה בטוחה יותר אם נתקלים
  בקושי.

זהו מצב פריסה **נוסף**, לא תחליף ל-dev המקומי הרגיל (client/server
כתהליכים נפרדים דרך Vite) — שלושתם נתמכים במקביל.

## 3. סטטוס המימוש

שלב התכנון הסתיים; הפרויקט במימוש פעיל. ראו `docs/roadmap.md` לפירוט
מדויק של מה קיים, מה נבדק, ומה עדיין לא נבנה בכל שלב.
